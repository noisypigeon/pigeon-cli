- CLI-0155: installs `rclone` in the container image from a **pinned, checksum-verified upstream binary**, closing [#96](https://github.com/noisypigeon/pigeon-cli/issues/96) — the image had never installed the one dependency *every* job needs since CLI-0132/0133 routed all data operations through it, so a container built from this repo failed on the first rclone invocation of any job. Debian's was **checked, not assumed**: every flag `core::rclone` passes predates 1.60, `LsjsonEntry` deserializes only `Name`/`Path`/`Size` with serde defaults, and the JSON-log parser defaults every field and skips unparseable lines, so apt would *work* — the argument against it is that bookworm ships **1.60.1 (2022)** against a project developed on **1.72+**, and a 15-version skew between where behaviour is verified and where it runs is a bad trade for one saved line in a codebase already bitten twice by something resolving to nothing and exiting 0 (CLI-0139, CLI-0140). Fetched in a dedicated builder stage so `curl`/`unzip` never reach the runtime image (confirmed absent from the shipped one), and verified against upstream `SHA256SUMS` — **proved load-bearing** by appending a byte to the archive mid-build and watching `sha256sum` fail it, with a nonexistent version separately failing at `curl`. **The build arg is `PIGEON_RCLONE_VERSION`, not `RCLONE_VERSION`**, and that is not cosmetic: rclone configures itself from `RCLONE_<FLAG>` environment variables, so the obvious name is read as the `--version` *boolean* flag and kills every rclone invocation in the stage with `strconv.ParseBool: parsing "1.75.2"` — found by the stage's smoke test *after* download, checksum and extraction had all succeeded, which is precisely the argument for keeping that line. Verification is deliberately scoped to what the container is worth today — `rclone v1.75.2` executes in the shipped image and all five converters resolve on `PATH` — and a complete in-container job run is explicitly **not** claimed, since every job resolves its buckets through a keyring alias into a generated S3 config and a local directory is not expressible as one. Amends CLI-0087 and CLI-0154 ([#115](https://github.com/noisypigeon/pigeon-cli/pull/115)).

Recorded with an honest caveat rather than smoothed over: the `.key` fixture is a Keynote **theme** document (`.kth`) shipped inside `Keynote.app` — the same IWA zip container, 21 `.iwa` members, same filter — not a user-saved presentation, because Keynote's scripting interface blocks on its theme chooser headlessly. Also repairs docs that claimed to describe *current* behaviour and did not — `transform/mod.rs` and `format.rs` were **three** ADRs behind, so this fixes CLI-0149 and CLI-0153 drift too, and `format.rs` had come to contradict its own `output_extension` doc 290 lines below — plus `README.md`'s single description of the command, `strict_stem`'s excluded-family list, the `--audio-quality` gating doc, `placement.rs`'s and `media.rs`'s module docs, and two "ffmpeg-capability gap" comments now four binaries wide. Removes a stray zero-byte `check_ffmpeg_available` committed at the repo root by `cd718e7`. `.claude/skills/analyze-job-run/` deliberately untouched — it enumerates no kinds, extensions or binaries, so CLI-0151's same-PR rule is not triggered. No behaviour change; 564 tests unchanged ([#113](https://github.com/noisypigeon/pigeon-cli/pull/113)).

## [0.4.36] - 2026-10-14

- CLI-0154 (implementation): adds the thirteen document input kinds to `job run transform`, taking `InputFileType` from 16 variants to 29 and shipping its **first input family whose members do not share one output extension** — `doc`/`docx`/`pages`/`rtf`/`pptx`/`key` to `.pdf` via `soffice`, `epub` to `.pdf` via Calibre's `ebook-convert`, `pdf` copied through, `txt` copied through, `md`/`markdown`/`mkd` and `rst` to `.txt` via `pandoc -t plain`, `textclipping` to `.txt` in-process, and `tsv` to `.csv` in-process. The load-bearing piece is the **private-key guard**: LibreOffice imports an OpenSSH key named `.key` as a plain-text Writer document, **exits 0**, and writes a valid PDF with every base64 line legible in it — and CLI-0149's "a non-empty file where the next stage expects one" check, which exists *because* soffice's exit code is unreliable, passes it, because there genuinely is one. So `documents::ensure_keynote` rejects the **input**, requiring the iWork zip magic *positively* rather than blocklisting `-----BEGIN`, since the set of things that are not Keynote is open-ended (PKCS#8, PKCS#12, DER); the refusal is classified wrong-input-kind so CLI-0143 drops the local copy, and an end-to-end test asserts nothing reaches the destination and nothing lingers locally. Also replaces `required_converter_available`'s catch-all arm — which routed every unlisted kind to `check_ffmpeg_available` — with an exhaustive `match` returning a `Converter` enum: that arm was an **undocumented fifth** no-compiler-help touchpoint, introduced by CLI-0149 and missed by its own §7 list, under which a `docx` run would have passed preflight on a host with no LibreOffice and then failed on the first file. CLI-0149's hardened `soffice` runner is parameterized by target extension into a new `transform/soffice.rs` — per-invocation `-env:UserInstallation` profile, 300 s timeout and deliberately-untrusted exit code all intact — at two consumers rather than the usual three, stated as a parameterization of one function rather than a speculative hoist. Naming needed **no change**: `compute_destination_name` is already collision-free by construction (CLI-0112 §5), which is the entire answer to the copy-through collision requirement even with seven kinds converging on one `destination:pdf/` prefix, and `strict_stem` is deliberately **not** widened since every document kind is single-output and widening it would duplicate rather than migrate (CLI-0151). No `is_document()` predicate is added, recording where CLI-0153's one-predicate-per-family shape stops working, and `tsv` is kept out of `is_spreadsheet()` because that predicate drives three unrelated behaviours and would be right for only one. New direct dependency `plist`; the Dockerfile gains `libreoffice-writer`, `libreoffice-impress`, `calibre` and `pandoc` (its existing `libreoffice-calc` opens neither Writer nor Impress formats, so six kinds would have failed on the current image), with all four package names checked against the bookworm index rather than assumed. **564 tests, from 514**, and every document kind is exercised end to end against fixtures built in-test — an RTF converted by `soffice` itself into `.doc`/`.docx`, a flat ODP into `.pptx`, an `.epub` built by Calibre, a clipping built via `plist` — with **none of the new tests skipping** on this host. The ADR moves `Proposed` to `Accepted`; `pages` and `key` stay evidenced only by the filter-registry inspection, since no iWork file exists on the authoring machine and neither converter can author one ([#112](https://github.com/noisypigeon/pigeon-cli/pull/112)).

## [0.4.35] - 2026-10-14

- CLI-0154: adds thirteen document input kinds across fifteen CLI spellings to `job run transform` — `doc`, `docx`, `pages`, `rtf`, `pptx`, `key` and `epub` to `.pdf`, `pdf` copied through, `txt`, `md`/`markdown`/`mkd`, `rst` and `textclipping` to `.txt`, and `tsv` to `.csv` — making it the **first input family whose members do not share one output extension**, and taking `InputFileType` from 16 variants to 29. **Three findings shaped it more than the variant list did, all measured rather than assumed.** LibreOffice imports an OpenSSH private key named `.key` as a plain-text Writer document, **exits 0**, and writes a valid 17,558-byte one-page PDF with the `-----BEGIN OPENSSH PRIVATE KEY-----` banner and every base64 line of key material legible in the output — and every check this codebase applies passes it, because CLI-0149 substitutes "a non-empty file where the next stage expects one" for the exit code precisely *because* the exit code is unreliable, and here there is a large, well-formed PDF; so without a guard a `--input-file-type key` run would transcribe private keys into PDFs and push them to the destination bucket, where nothing distinguishes them from legitimate Keynote output. The guard therefore rejects the **input** rather than checking the converter's output, sniffing for the iWork zip magic — a *positive* check, since the set of things that are not Keynote is open-ended and a blocklist would have to anticipate PKCS#8, PKCS#12, DER and whatever else arrives with that extension — and composes with CLI-0143 so the local copy is deleted and the key does not linger on the transform host; stated plainly, and not hidden, is that this prevents a key being *converted*, not *pulled*. Second, LibreOffice's EPUB filter is **EXPORT-only** (`writer_EPUB_Document` carries `flags=EXPORT ALIEN 3RDPARTYFILTER` with no IMPORT counterpart anywhere in its registry, while every other routed kind has one — `MS Word 97`, `MS Word 2007 XML`, `Rich Text Format`, `Impress MS PowerPoint 2007 XML`, `Apple Pages`, `impress_AppleKeynote`), which is why `epub` alone takes Calibre and why this adds two external binaries rather than one. Third, a modern `.textClipping` is a **data-fork binary property list**, not the resource fork expected (measured: 295 bytes, no `..namedfork/rsrc`, one `UTI-Data` key holding three encodings one of which is already UTF-8), which is what makes it a cheap kind to include rather than the awkward one it looked like. Also closes an **undocumented fifth** no-compiler-help touchpoint from CLI-0149 §7 — `required_converter_available`'s `_ => check_ffmpeg_available()` means any variant added without touching it silently demands `ffmpeg` and never checks its real converter, so a `docx` run would pass preflight on a host with no LibreOffice — replaced with an exhaustive `match` returning a `Converter`, putting it back in the compiler's hands. Destination naming needed **no change**: `compute_destination_name` is collision-free by construction (CLI-0112 §5), which is the whole answer to the copy-through collision requirement even with seven kinds converging on one `destination:pdf/` prefix; and **`strict_stem` is deliberately not widened** to the document kinds, because CLI-0151 scoped it to multi-output kinds and this job never deletes at the destination, so widening it would **duplicate** rather than migrate, at the 67%-of-inputs rate measured there. No `is_document()` is added either, recording where CLI-0153's one-predicate-per-family shape stops working — it holds only because each of those families has one output extension, so predicate and branch coincide; documents span three, and `tsv` is likewise kept out of `is_spreadsheet()`, which three unrelated concerns consult and which would be right for only one of them. CLI-0149's hardened `soffice` runner (per-invocation `-env:UserInstallation` profile, 300 s timeout, exit code not trusted) is parameterized into its own `transform/soffice.rs` at two consumers rather than the usual three, stated as a parameterization of one function rather than a speculative hoist — the alternative being a byte-for-byte copy differing in one string literal. `md`/`rst` **lose link URLs and all inline markup** via `pandoc -t plain`, chosen over lossless copy-through because this family is defined by its output being readable prose. Measured cost: a cold per-invocation LibreOffice profile is 1.07 s against 0.45 s warm, so ~0.6 s of every `soffice` file builds a profile that `ScratchDir` then deletes, making a document run far more expensive per file than an image run. The Dockerfile's `libreoffice-calc` does **not** open Writer or Impress formats, so six of these kinds would fail on today's image; it gains `libreoffice-writer`, `libreoffice-impress`, `calibre` and `pandoc`. **Status is `Proposed`, not Accepted**: `ebook-convert` and `pandoc` are absent from the authoring machine and no iWork file exists on it, so the `epub`, `md`/`rst` and `pages`/`key` routes are unverified, gated the same way CLI-0149 gated its own `.numbers` claim. Amends CLI-0112, 0149, 0151, and 0153 ([#109](https://github.com/noisypigeon/pigeon-cli/pull/109)).
