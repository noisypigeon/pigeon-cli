# Changelog

All notable changes to the `pigeon-cli` crate are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

- ADR-0149: adds four spreadsheet input kinds to `pigeon job run transform` (`numbers`/`xlsx`/`xls`/`csv`, all outputting `.csv`, so `source:xlsx/` -> `destination:csv/` falls out of ADR-0138/0139's prefix inference with no new code) and with them **this job's first input kind where one input file yields several output files**: a workbook's sheets each become their own CSV. Not a fifth arm on an existing pattern -- the one-output-per-input assumption is load-bearing in five independent places, **three of which run before any bytes are downloaded**, and the hard one is ADR-0124's pre-pull skip filter, which rests on `compute_destination_name` being a pure *forward* function of `(source_path, relative_path)` needing no file content while **a sheet count is not knowable without opening the file**. Resolved in the naming rather than by weakening that filter: all sheets of one input share the existing 16-hex digest (hash input byte-for-byte unchanged) as a *group key*, with `-{nn}of{tt}-{slug}` appended -- `nn` preserving workbook sheet order, the only place that ordering survives into the output, and `tt` making a half-pushed group **detectably** incomplete so a rerun completes it, where the obvious "any member present" test would have treated such a workbook as done forever and silently lost that sheet. A single-sheet workbook and a `.csv` copy-through keep **today's exact plain name**, so the existing scheme is literally unchanged for every input with one output and the suffix appears only where it carries information. The group key stays pre-pull computable, so ADR-0124's filter survives as a group-completeness test over the same single destination listing, and the destination stays **flat** -- which is the one of the five places needing no change at all, since encoding the grouping in the *name* rather than a per-workbook directory keeps `list_existing_filenames` non-recursive and keyed on `entry.name`. `transform` also still **never deletes at the destination**: the obvious alternative (delete the partial group, then redo) would have broken ADR-0112's only-ever-copies property for the first time, where instead already-landed sheets are re-pushed and absorbed by `copyto`'s own skip-if-unchanged (ADR-0116). Engine is `calamine` in-process for `.xlsx`/`.xls` -- sheet list in workbook order with exact names, full control of output filenames, and tests that run in CI with no binary installed -- with `.numbers` routed through `soffice --convert-to xlsx` into the *same* calamine path rather than letting LibreOffice emit CSV directly, since its all-sheets export (filter token 12 = `-1`) names outputs by sheet *name* with no index, so workbook order would be unrecoverable and the filenames would be its choice rather than ours; that keeps **one** multi-sheet code path and confines LibreOffice to one kind, which is also what makes dropping `Numbers` a clean subtraction if it fails. `-env:UserInstallation` per invocation is **not optional** (concurrent `soffice` calls otherwise contend on one profile and serialize or fail), the output's existence and non-emptiness are verified rather than its exit code trusted, and the call is wrapped in a timeout -- hanging being `soffice`'s known failure mode, and a difference from every existing converter rather than a convention. `.csv` is byte-for-byte copy-through via the existing `media::copy_through`, ADR-0112's jpeg-to-jpg precedent. Records cell-rendering decisions rather than leaving them to be discovered from output: ISO-8601 dates via calamine's `dates` feature (a bare serial like `45234` being the single likeliest silent corruption in this path), **cached** formula values, empty sheets skipped and excluded from `tt` so it stays a deterministic function of content, hidden sheets included, a `MAX_SHEET_CELLS` cap since `worksheet_range` materializes a sheet entirely in memory, and `~$*` Excel lock files filtered at both dispatch choke points the same shape ADR-0130 used for AppleDouble stubs. Also moves the binary preflight to *after* `--input-file-type` resolves, so a `csv`/`xlsx`/`xls` run no longer demands `ffmpeg` it never uses and a `numbers` run demands `soffice` instead -- the first time this job's external-tool requirement depends on its own flags, made exact rather than a union. No metric label *values* change, so dashboards are unaffected. **Status is `Proposed`, not `Accepted`**: `libetonyek`'s fidelity on recent `.numbers` files is recorded as *not verified* (no `soffice` on the authoring machine, no real `.numbers` file converted), and the Verification section gates the Status on one. Flags, without fixing, that the Dockerfile installs `ffmpeg` but **not `rclone`**, which every job requires on `PATH` -- so either the image cannot run any job or production provisions it by a path this repo does not record. Amends ADR-0112, 0120, 0122, 0124, and 0139 ([#93](https://github.com/noisypigeon/pigeon-cli/pull/93)).

- ADR-0148: drops the `minio` dependency by migrating its last two call sites onto ADR-0132's `core::rclone`, resolving the "explicitly not dead" exception ADR-0147 §3 recorded and deleting `src/commands/keyring/bucket/client.rs` entirely (~370 lines; `Cargo.lock` sheds 818). **Tracing it surfaced a latent bug that made this more than a mechanical migration**: `write_sandboxed_config` wrote `BucketConfig::secret_key` straight out of the keyring, never through `credentials::resolve_secret`, so ADR-0087's `PIGEON_SECRET_<ALIAS>` override **has never reached any rclone-addressed operation** -- `transform`'s pull and push, `deduplicate`'s three legs (ADR-0133), `rclone copy`/`delete`, i.e. every job's actual data path. It appeared to work only because the two surviving `minio` sites resolved the secret themselves before calling, which is exactly why a naive migration would have *silently taken a working override away* for report upload. Fixed first as a prerequisite rather than last as a consequence, and verified against the real binary (a stored `WRONG-STORED-KEY` with `PIGEON_SECRET_PROBE_BUCKET=CORRECT-ENV-KEY` yields `secret_access_key = CORRECT-ENV-KEY` in the generated config, and the stored value without it). `report_upload`'s three artifact uploads go through `CopyTo` with `emit_upload_metrics: false` -- counting instrumentation *about* a run in `pigeon_upload_bytes_total` would inflate every job's transferred-bytes series by a constant unrelated to the data it moved -- which removes the secret from that whole path: `resolve` returns a `BucketConfig` rather than `(BucketConfig, String)`, `upload_run_artifacts` loses its `secret` parameter, and the `report_secret` local disappears from 6 call-site pairs across 5 wizards. ADR-0010's verify-before-save is **kept**, via `Lsjson` against an ephemeral one-entry `Store` written by the *real* `write_sandboxed_config` -- not a second emitter, so ADR-0140's two-section `alias` -> bucket shape cannot drift -- at a per-pid `rclone-probe-<pid>.conf` beside `keyring.toml` rather than in the OS temp directory, since it carries a secret access key and that directory is the one already trusted with those at `0600` (ADR-0135). The ordering problem it solves is real: the candidate is validated *before* it is in the keyring, while `execute` unconditionally reads the keyring-derived config, so `RcloneCommand` gains a **defaulted** `config_path()` -- the same shape `retry()` already has, leaving all four existing implementors untouched. **The tri-state is genuinely lost**: `HeadBucket` distinguished absent from could-not-tell, `lsjson` does not, and recovering it would mean matching rclone's stderr -- issue [#63](https://github.com/noisypigeon/pigeon-cli/issues/63)'s version-fragile pattern -- so the outcome collapses to verified / `failed to verify bucket '<name>': <stderr>`, which still names `NoSuchBucket` when that is the cause. Deleting `client.rs` also finally removes **four `pub` functions with zero callers that survived ~130 ADRs** (`ObjectEntry`, `list_buckets`, `list_objects`, `download_object_to_file`) because a fully-`pub` module path makes `dead_code` blind -- this crate's one blind spot in an otherwise clippy-proven census, filed as out of scope -- plus `UploadOutcome`, vestigial in a subtler way (both variants constructed, so the lint stayed quiet, but the sole caller discarded the value), and with it the entire ETag recipe and the `md5` dependency that existed solely to compute a number nobody read. Prunes `minio` and `md5`, plus `time`'s `"formatting"` feature, which nothing has ever used -- asserted by grep and a build rather than by inspection, since ADR-0147 shipped two unused dependencies past an otherwise-clean gate. **`keyring add`/`modify bucket` now require `rclone` on `PATH`**, new for a `keyring` command. Also corrects user-visible staleness: `Cargo.toml`'s description and `src/cli.rs`'s `#[command(about)]` (what `pigeon --help` prints) still read "authenticate, sink, and transform", product verbs from ADR-0001/0005/0006 all since reversed; `CLAUDE.md` illustrated `mise run pigeon` with `-- email list`, a group folded into `keyring` by ADR-0022; the `analyze-job-run` runbook named `pigeon_upload_attempts_total` in one place while stating two sections later that it no longer exists, ADR-0147 having fixed the second mention and missed the first; and `adr-issue.sh`'s label descriptions claimed an OS keychain (retired by ADR-0135) holding encryption keys (removed by ADR-0147). **Recorded as not verified**: whether `no_check_bucket = true` masks a missing bucket for a *listing*. `dialoguer` requires a TTY, so `keyring add bucket` cannot be driven from a test, and confirming it needs a human at a terminal with real credentials; if it does mask it, the symptom is ADR-0010's pre-existing risk returning (a typo'd bucket accepted, rejected at first job run), not a new failure mode. Amends ADR-0009/0010, 0017, 0087, 0089, 0091, 0100, 0132, 0136, and 0147 ([#90](https://github.com/noisypigeon/pigeon-cli/pull/90)).

- ADR-0147: removes `pigeon job run email-sync` (ADR-0007/0021) and `pigeon job run email-pull` (ADR-0081) now that ADR-0146's `email import` has landed, taking `pigeon` from 7 job types to 5, and removes **client-side encryption** with them -- `core/crypto.rs`, the `encryption-key` keyring kind, `Entry::EncryptionKey`, `BucketConfig::encryption_key_alias`, and the `aes-gcm-siv`/`hkdf`/`hmac` dependencies, explicitly reversing ADR-0025, ADR-0026, and ADR-0027, since `email-sync` was the only caller of `Encryptor::encrypt` anywhere in the crate and a keyring kind nothing can consume is worse than none (ADR-0134's clean-sweep precedent). Also rewrites README's `## Commands` section rather than patching it -- every `job run` bullet was wrong, since **ADR-0134 removed `decrypt-files` without ever touching that file** -- and prunes the `analyze-job-run` runbook, which likewise still listed `job.decrypt-files` despite ADR-0134 claiming a clean repo-wide grep and had never gained `job.email-import` despite ADR-0146 shipping it, both against that file's own "update this cheat sheet in the same PR" rule. ## [0.4.27] - 2026-10-13

- ADR-0146: adds `pigeon job run email import`, a third and deliberately minimal email job -- reads an IMAP account named by a keyring alias and delivers each message's raw `.eml` **plus its unpacked attachments** to an rclone-addressed `--destination`, with deduplication, indexing, renaming, transforms, and encryption all permanently out of scope: it moves bytes and nothing else. Lands as a nested `JobType::Email` group (`job run email import`, mirroring ADR-0110's `rclone copy`/`rclone delete`), taking `pigeon` to 7 job types, and is the **first email job on `core::rclone`** and the first to call ADR-0145's `prepare_rclone` -- both siblings are `minio`-only. The load-bearing decision is pacing: **`--messages-per-minute` (default 120)** is the run's throughput governor, built on a pure, clock-free `reserve()` whose two properties are the point -- concurrent callers *stagger* rather than burst, and idle time is **never** paid back, so a run resuming after a retry cannot fire a banked backlog at the server. There is deliberately **no `--concurrency`** flag (the pacer, not worker count, sets the rate, and a knob that does not control what its name implies would be worse than none), no `--upload-only` (meaningless when `.pushed` records *delivery* rather than local completion), no `--encryption-key`, and no `--transfers`/`--checkers`/`--tpslimit` (`CopyTo` accepts none -- a single-file `copyto` has no transfer set to parallelize); every absence is asserted by a negative CLI test, plus a companion asserting `--push-concurrency` *is* present so the `--concurrency` negative is not satisfied by a substring. Three retry layers replace the sibling jobs' **15 seconds** of total patience (`(3, 5s)`, roughly an order of magnitude short of the real 74-second DNS blackout ADR-0144 measured): connect `(4, 30s)`, batch requeue `(3, 30s)`, and a `RecoveryGate` that elects one prober per outage so a **long** outage costs the run one shared wait rather than one per in-flight item, latching after its budget so remaining work fails fast instead of re-paying it -- ADR-0144's `EndpointGate` lesson applied before a failed run rather than after one, and written generic over its classifier so it serves both the IMAP leg (`is_server_overloaded_error`, 6 rounds x 60s) and the push leg (reusing `core::rclone::is_endpoint_unreachable_error`, 4 rounds x 30s). Delivery is per-message -- fetch -> `rclone copyto` -> **delete the local copy, on success and failure alike** -- a deliberate divergence from ADR-0124's retain-on-failure rule and strictly safer than it, since a failed `.eml` is still on the IMAP server undamaged where a rerun refetches it anyway (ADR-0143's "non-destructive, still at the source" reasoning), which bounds local disk to the in-flight window **unconditionally** and makes ADR-0143's ~80 GiB retention pathology structurally impossible rather than merely unlikely. Skips the `BODYSTRUCTURE` manifest pass entirely, so the pre-run table is counts only with no `BYTES`/`ATTACHMENTS` columns: that pass is a second full-corpus traversal which, at this job's deliberately throttled pace, costs about as much as the fetch it would be estimating -- ADR-0032/0034's own reasoning inverted for this job alone, their behavior untouched where they describe it. Ships ADR-0098/0130/0141's observability lessons up front instead of retrofitting them after an undiagnosable run: span propagation through every `tokio::spawn` (the exact bug that left all 1,449 of `transform`'s per-file events with no `command` span), phase-boundary `info!` lines, a per-category `FailureBreakdown` with two counters deliberately outside its sum, and `set_macro_phase` **never emitted** at all, following ADR-0130's precedent -- that gauge encodes a one-way local-then-upload transition a job pushing inline never performs. Also records, in §2, three hoists a third consumer would normally trigger but which are declined with a one-PR lifetime, and in §10 the full forced-deletion census for the follow-up. Defers, per ADR-0031: hoisting `RecoveryGate` into `core::rclone` on its third consumer, and a cheaper pre-run size estimate. **ADR-0147 will remove `email-sync` and `email-pull`**, taking `pigeon` back to 5 job types ([#85](https://github.com/noisypigeon/pigeon-cli/pull/85)).

## [0.4.26] - 2026-10-13

- ADR-0145: adds a root-level `--keyring-path` global flag overriding where `keyring.toml` is read, with precedence **flag > `PIGEON_CONFIG_DIR` > OS config dir** -- the flag names the *file*, the env var still names the *directory*, so neither replaces the other. Declared `global = true`, so it parses *after* the subcommand (`pigeon job run transform --keyring-path /etc/pigeon/keyring.toml --input-file-type mp4`), and reaches the email jobs and `pigeon keyring` as well as the three job types that motivated it. Resolved once in `main` into a `OnceLock` rather than threaded through each wizard: `core::rclone::execute` appends `--config <rclone_config_path()>` to *every* invocation from deep below any wizard, so threading it would mean changing `RcloneCommand::run`'s signature and every `Copy`/`CopyTo`/`Lsjson`/`Purge` call site, through the code ADR-0132 consolidated precisely so callers would stop re-deriving subprocess scaffolding (`observability::LOG_FILE_PATH`'s precedent). `Store::default_path` is renamed `resolve_path` -- with two overrides ahead of the default, the old name described only its last branch -- and both it and `rclone_config_path` gain pure `resolve_path_from`/`rclone_config_path_beside` halves so the precedence stays unit-testable despite a `OnceLock` that can only be set once per process (ADR-0143's `circuit_breaker_should_trip` precedent). The generated `rclone.conf` keeps following the keyring's own directory, so `--keyring-path /etc/pigeon/keyring.toml` writes `/etc/pigeon/rclone.conf`, preserving ADR-0136's sibling invariant, keeping the two files that carry the same plaintext credentials together, and narrowing the concurrent-rewrite race ADR-0136's Consequences named. Hoists six byte-identical job-wizard keyring loads into `shared_wizard::load_keyring`, which **refuses an explicitly-passed path that does not exist** -- `Store::load` treats any missing file as an *empty* store, correct for a first run at the default location but wrong for a path an operator named outright, where a typo otherwise surfaced much later as `no bucket-config named '...'`, naming neither the real problem nor the path (the same silently-did-nothing failure ADR-0140 closed for `Lsjson`); the guard lives there and deliberately not in `Store::load`, since `pigeon keyring add` must still create a keyring that does not exist yet. Hoists three byte-identical rclone preflights into `shared_wizard::prepare_rclone`, whose fourth call site **fixes two real latent defects**: `deduplicate` never called `write_sandboxed_config` at all, despite all three of its data legs (`manifest`'s `Lsjson`, `worker`'s per-item `CopyTo` and bulk `Copy`) being alias-addressed rclone calls that read that file -- so it ran against whatever a previous `transform`/`rclone` run happened to leave behind, or nothing at all, and a `pigeon keyring modify bucket` never reached it, directly contradicting ADR-0136 §2's "regenerated fresh from the current keyring state every time" guarantee (latent rather than observed only because the one real deployment co-locates every job on one host) -- and never checked `rclone` was on `PATH` either. Completes ADR-0132 §1's `check_rclone_available` consolidation, which had left two wrappers behind that `clippy -D warnings` now forces out, preserving `rclone::worker`'s better error text in the shared helper. Amends ADR-0022, ADR-0135, and ADR-0136 ([#84](https://github.com/noisypigeon/pigeon-cli/pull/84)).

## [0.4.25] - 2026-10-13

- ADR-0144: survives a destination-endpoint outage, and explains a case-colliding source key. A real `job run transform --input-file-type jpg` run pushed 37,955 files cleanly then exited 1 with **277 failures from two unrelated causes**. **275 push failures** were one continuous 74-second DNS blackout: all 275 per-file logs carry *only* `dial tcp: lookup s3.fr-par.scw.cloud: no such host`, and the macOS unified log shows `mDNSResponder` returning a negative answer for both A and AAAA over `utun6` -- a ProtonVPN WireGuard tunnel that is this host's **only** primary resolver -- while `pmset` shows 5 sleeps totalling 3,102s, corroborated independently by `elapsed_ms=15489289` (monotonic, so sleep-excluding) sitting 3,072s under the wall-clock span. The amplifier was pigeon's own: `CopyTo::retry()`'s `(3, 2s)` is a **6-second** budget against a 74-second outage, and a negative DNS answer is negative-TTL cached, so retrying that fast is structurally guaranteed to reproduce it. Raises it to `(4, 30s)` (~5 min) -- which alone would have fixed this incident, since the push semaphore already caps concurrent pushers at `--upload-concurrency`, a correction to the first analysis that is recorded in the ADR rather than dropped -- **plus** a new `EndpointGate` electing one prober per outage (others park on a `watch` channel instead of spawning doomed `rclone` subprocesses) so a *longer* outage costs one shared wait rather than every successive batch re-paying the budget, latching after 4 fruitless rounds; it pauses-and-resumes rather than aborting, unlike ADR-0121's transcode breaker, and a push failure still retains both local copies (ADR-0124/0143). Endpoint-level failures are classified by a new `core::rclone::is_endpoint_unreachable_error`, homed there rather than in `transform::media` because it matches *rclone's* output, and kept a separate predicate per ADR-0143's precedent -- these errors are retryable, but they are **shared** by every concurrent transfer, which is what licenses handling them once per run. The **2 pull failures** were two S3 keys differing only in extension case (`IMG_0260.JPG`/`IMG_0260.jpg`) colliding on case-insensitive APFS; rclone resolves that itself, logging `Duplicate object found in source - ignoring` at **`notice`** level with its error count left at zero, which is exactly why ADR-0130's `rclone_errors=0, undelivered_files=2` cross-check fired. Real data gaps, not false positives -- and `compute_destination_name` hashes case-sensitively, so the variants never collide at the *destination*. Now detected up front in `files_needing_pull` and warned with every colliding key named before the pull starts, and ADR-0130's undelivered-file message -- *false* for this class, since rclone did report the file -- is replaced per-class via a pure `undelivered_detail`. Adds `tokio`'s `test-util` as a **dev-only** dependency for `start_paused`'s virtual clock. Defers, per ADR-0031: actually pulling both case variants, which needs the local-path layout changes ADR-0124's GC and the initial `source/` scan both depend on ([#83](https://github.com/noisypigeon/pigeon-cli/issues/83)). Amends ADR-0121, ADR-0130, ADR-0132, and ADR-0143 ([#82](https://github.com/noisypigeon/pigeon-cli/pull/82)).

## [0.4.24] - 2026-10-13

- ADR-0143: bounds the damage when `job run transform` is pointed at the wrong `--input-file-type`. ADR-0142's has-a-video-stream guard was correct -- no video is ever converted to audio-only -- but **not bounded**: tracing what happens to each rejected file found that (a) every rejected file's local source copy was retained under ADR-0124's retain-on-failure rule, and (b) ADR-0121's circuit breaker required **unanimity** across its first 20 completions, so a single interleaved success disarmed it *permanently* (`circuit_breaker_samples` only counts up to the sample size, after which the trip condition is never re-evaluated). Composed, a `mp4-audio` run over the real 7289-file bucket (~6.6% genuinely audio-only) would fail ~6809 files while retaining all of them locally -- roughly 80 GiB -- until free space hit this job's own 2 GiB `check_disk_space` floor and files began failing for an unrelated reason that obscured the real one. Fixes both halves: a wrong-input-kind failure now deletes its local source copy (non-destructive -- the file is undamaged and still at `--source`, where a rerun pulls it from anyway), classified by a new `media::is_wrong_input_kind_error` kept deliberately separate from `is_non_retryable_transcode_error` since the two answer different questions; and the breaker trips on `CIRCUIT_BREAKER_TRIP_THRESHOLD` (18) of 20, with the decision extracted into a pure `circuit_breaker_should_trip` so the threshold is unit-testable independently of concurrent completion ordering. Every *other* failure class keeps ADR-0124's behavior untouched -- the pre-existing mostly-healthy-batch test's "corrupt `bad.png` is retained" assertion is left unmodified as the guard proving that. Also promotes the two guard substrings to named consts (they match pigeon's *own* message text, not `ffmpeg` stderr, so they are robust only as long as producer and matcher cannot drift), and stops the abort message attributing the cause solely to the host's `ffmpeg` build now that a wrong `--input-file-type` is at least as likely. Defers, per ADR-0031: checkpointing failed files so a rerun skips them ([#80](https://github.com/noisypigeon/pigeon-cli/issues/80)), and preserving `transform-report.txt` on a tripped-breaker abort ([#81](https://github.com/noisypigeon/pigeon-cli/issues/81)). Amends ADR-0121, ADR-0124, and ADR-0142 ([#79](https://github.com/noisypigeon/pigeon-cli/pull/79)).

## [0.4.23] - 2026-10-13

- ADR-0141: fixes two independent defects found analyzing a real `job run transform --input-file-type mp4` run that pulled 7289 files cleanly but failed 483 transcodes. **480 of those 483** were audio-only files -- voice-note recordings saved with an `.mp4` extension, confirmed via `ffprobe` as having no video stream at all -- routed into the video pipeline by `InputFileType`'s purely extension-based dispatch; `transcode_video`'s mandatory `-map 0:v:0` always failed on them with ffmpeg's raw `Stream map '' matches no streams` stderr, which named neither the file nor the cause, and which (matching no entry in `NON_RETRYABLE_SIGNATURES`) was retried twice apiece for a 100%-deterministic outcome, costing ~960 wasted ffmpeg invocations and ~480s of pure backoff. A new `has_video_stream` check rejects such an input before ffmpeg runs, with a message naming the real problem, and its signature joins the non-retryable list. Separately, `transform`'s per-file `tokio::spawn` **never propagated the ambient tracing span** -- the exact bug class ADR-0098 fixed for `deduplicate`/`pull_transform`, never applied here -- so all 1449 per-file WARN/ERROR events from that run landed in `pigeon.jsonl` with no `command` span at all, making the `analyze-job-run` skill's documented `spans[].command` filter return **zero** hits for every one of the 483 failures; fixed with the same capture-then-`.instrument()` shape, plus a structured `relative_path` field on the retry loop's own events (`process_one`'s span deliberately stays at `debug` per ADR-0099's log-volume reasoning). - ADR-0142: adds `job run transform --input-file-type mp4-audio`, making the 480 files ADR-0141 can only diagnose actually processable -- a new `InputFileType::Mp4Audio` transcoding an audio-only `.mp4` to Opus in an Ogg container (`-c:a libopus -b:a 48k -application audio -f opus`, output extension `opus`). Opus is the best quality-per-bit codec for this content and costs nothing for the intended future transcription work (every pipeline decodes to PCM first); 48k rather than the speech-tuned 32k because the content is archival audio of *unknown* type, some clips possibly music, mirroring ADR-0122's deliberately-better-than-conventional CRF reasoning. Amends ADR-0122 and ADR-0141 ([#78](https://github.com/noisypigeon/pigeon-cli/pull/78)).

## [0.2.0] - 2026-09-25

Unstable. Introduces a trait-based core architecture, a unified keyring, and end-to-end client-side encryption for `email-sync` uploads.

- ADR-0028: `pigeon job run decrypt-files` decrypts `*.enc` files from a local input directory into an output directory using a configured encryption key — `core::job::Job`'s second real implementor, alongside `email-sync`.
- ADR-0027: An encryption key can default to a bucket-config (chosen by alias in `keyring add/modify bucket`) and still be overridden per run via `--encryption-key` or interactively; non-interactive runs now pick up that default automatically instead of always skipping encryption.
- ADR-0026: `pigeon keyring add/modify encryption-key` manages symmetric encryption keys — generated or imported — in the OS keychain, selectable by alias wherever a key is needed.
- ADR-0025: `email-sync` uploads can be encrypted client-side with AES-256-GCM-SIV and a content-derived deterministic nonce, so identical plaintext still dedups correctly against S3 ETags even when encrypted.
- ADR-0024: The upload phase now runs concurrently across every selected identity (previously sequential), with its own progress bar and per-file retry-with-backoff.
- ADR-0023: Core logic reorganized into trait-based `src/core/` (`Job`, `Transform`, `Dedup`, `KeyringEntry`, `WizardInput`) with concrete implementations moved to `src/commands/`.
- ADR-0022: `pigeon email authenticate` and `pigeon dataops bucket-config` are replaced by one `pigeon keyring add/modify/delete/list`, backed by a single `keyring.toml` and OS-keychain service.
- ADR-0021: `pigeon job run email-sync` replaces `pigeon email sync` with a wizard that resolves identities/concurrency/upload target, batches work across every identity's mailboxes, and shows a pre-run manifest summary.
- ADR-0020: Dedup and transform primitives (`ContentIndex`, filename sanitization, etc.) genericized for reuse beyond email.
- ADR-0019: Sync now runs fetch → transform+dedup → upload as ordered phases with an `.uploaded` checkpoint, instead of uploading inline per message.
